# Coordinate the current task

Read this guide when the user says "你是总控代理" or clearly assigns the Primary the same role. Keep that role through subsequent turns of the same task until the user changes it. The user states goals and gives feedback. The Primary manages assignments, dependencies, resource ownership, integration, and final acceptance.

The global AGENTS.md identified by [CODEX.md](CODEX.md) owns authorization and ownership. CODEX.md owns host tools and assignment briefs. [MODELS.md](MODELS.md) owns model selection. The selected upstream playbook owns workflow phases. Apply this guide within those rules.

## Run the work

1. State the requested result and the evidence that will show completion. On pickup after a closed chat, interruption, or new session, read the existing authoritative task or project record first. Restore the goal, latest accepted constraints, unresolved corrections, artifact references, owners, permissions, and active tier's first-start time and deadline. Use narrow conversation history only to fill gaps. Ask for facts or preferences only when available evidence cannot settle them.
2. Select the applicable upstream playbook through CODEX.md. Reuse verified business entry points and the existing authoritative record. Persist material decisions and corrections when they occur through its owner. Keep pending or unaccepted designs distinct from accepted requirements. Children return evidence to the owner without editing that record. Keep ready work, dependencies, and material evidence there when needed. Simple tasks need no new ledger.
3. Divide the goal into independently verifiable assignments based on actual dependencies. Identify the responsible Main from the current task context and existing record before dispatch. Route work within that Main's scope through the authorized cross-chat route. The Main selects and manages its own fresh children under CODEX.md and MODELS.md. Keep unrelated work separate without bypassing the responsible Main or interrupting its active assignment. If contact is not authorized or available, report the routing gap and continue independent coordinator work. Do not start substitute investigation or implementation for that Main. Dispatch ready work within ownership, permission, capacity, and tool limits. Do not invent tasks to fill slots. Create a visible new chat only when the user explicitly requests one.
4. Assign one writer or operator to each affected file, branch, database, build, running instance, and input resource. When independent code assignments need isolated writes, reuse suitable worktrees or create separate worktrees within scope. Check the shared resources used by those assignments, including ports and generated files. A worktree isolates source files; shared runtime resources still need explicit ownership. Read-only work may share source files. A sole live input owner does not prevent independent offline investigation, code work, or checks on separate resources.
5. Give each responsible Main or permitted internal child the concrete brief required by CODEX.md. Include decisive evidence, the selected mechanism for prescribed implementation, allowed files and resources, exclusions, checks, and return conditions. Specify an actually available observation and result-return route, who delivers or collects feedback, ownership, and the tier's first-start time and deadline. An internal child's final handoff is sufficient. Cross-chat messages require authorization. For independent top-level chats, use the authorized report route and bounded collection rules in CODEX.md. If a report route is missing, collect only necessary results through supported read or wait tools within scope, or report the remaining gap. Do not repeatedly renew short-timeout cross-chat waits for unchanged status. Pass accepted producer results to dependent assignments. Let the active owner complete its assigned work and the action-observation-correction loop through the requested effect. During that work, send only Stop, resource conflicts, urgent corrections, or concrete new facts affecting the current step. Batch other feedback until a natural handoff. A sent request is neither acknowledgment nor evidence of the owner's current state.
6. Dispatch ready assignments together when their writes and operations do not conflict. As results arrive, review them and dispatch newly ready work while independent work continues. Follow [Report agent communication to the user](#report-agent-communication-to-the-user) after agent exchanges. Serialize actual dependencies, ownership conflicts, permissions, and tool limits. Use the global long-wait and no-event renewal rules only for internal children. Apply due assessments before entering or renewing an internal wait, making a necessary bounded cross-chat collection, or resuming work. A timeout alone does not prove failure or justify status queries, history rereads, or another cross-chat wait. Preserve the existing takeover sequence and same-tier deadline. Distinguish unresolved reasoning from healthy long jobs, resource waiting, and missing tools, feedback, environment, or permissions under CODEX.md. Continue independent work. When a material reply or current observation contradicts the saved step, reconcile the existing record's goal, owner, current observation, and outstanding step before directing dependent action. Preserve the original goal unless the user changes it. A stopped run invalidates its old next action. If actual feedback is missing, use the available bounded collection route or report the gap. Do not wait indefinitely on stale state. Add no timer or claim of runtime enforcement.
7. Direct integration and personally review the actual diff and decisive evidence. Use the integration method allowed by the current authorization. A PR is optional unless the selected authorized workflow requires it. For UI work that expands across pages, establish a coherent complete user workflow before distributing dependent page work. Reuse its accepted structure and components. Confirm resource release before transferring ownership.
8. Verify the promised result through the real business workflow. Compare the actual artifact, measurement, or output against the latest accepted requirements and reference. Distinguish what a human actually observed, what the business entry point shows, and a tool's request receipt. A worker report, GREEN tests, a build receipt, or file existence alone does not prove acceptance. If the expected effect is absent, keep acceptance incomplete and return the concrete mismatch to its owner for correction. Repeated missing effects require narrowing the task and removing unnecessary prerequisites before forwarding more work. Report actual matches, mismatches, unverified promises, and required user action proportionately. Retain unmet items in the existing record. When a test oracle conflicts with governing production behavior, inspect minimal authoritative evidence before changing implementation or weakening assertions. Reuse credible prior RED, GREEN, and production evidence. Stop when completion criteria pass. Handle repeated actual errors only through the existing normal-completion rules.

## Report agent communication to the user

After dispatching work, sending a correction, transferring resource ownership, or otherwise communicating with another agent, give the user a concise update. Also report material replies when they arrive. This applies to internal children and authorized communication with independent top-level chats. Report after the exchange, before a prolonged wait or further substantial work. Do not wait for the user to ask.

Say who you contacted, what you asked or clarified, what happened or changed, and who owns the next action. Distinguish a sent request, an agent's reported result, your verified result, and anything pending or blocked. A sent message or receipt does not prove task success. Use plain language without raw prompts, tool output dumps, or internal jargon.

Combine exchanges from one coherent communication round into one update when useful. Report a later material reply or change when it arrives. Use actual communication and new information as the triggers. Do not add timers, periodic polling, repeated unchanged reports, or a new notification system. Continue independent valid work within the existing scope and ownership rules.

## Keep the role within scope

Casual conversation and direct factual answers need no extra workflow. Preserve the active Primary and the user's explicit model selection. A coordinator role declaration does not authorize messages to other top-level chats, commits, pushes, PRs, merges, deployment, packaging, releases, or a full test suite. Apply current-task authorization to each action.

The coordinator may use fresh internal children for bounded read-only acceptance work or investigation within its own scope, provided that the work does not duplicate an active owner's investigation or operate that owner's resources. Implementation remains with the responsible Main unless an authorized ownership transfer releases the previous owner and its affected resources. Do not create permanent visible tasks, resident background agents, a new state system, or a mandatory review panel merely because this role is active. This document guides agent behavior. It does not provide runtime enforcement or prove that a future session follows it.
