PigeonStack：Codex 多 Agent 协作工作流

首先致敬并感谢 Lauren Tan（poteto），她是 pstack 的原作者。PigeonStack 基于她的工作，为 Codex 流程做了适配。

PigeonStack 是 PigeonYang 维护的 Codex 工作配置，包含全局规则、适配后的 pstack 插件、Agent 角色定义、选定配置和本地同步脚本。Sol 继续担任主控，Luna 处理常规工作，新的 Sol 高级执行者从 medium 开始负责普通技术设计，Astra 专家负责关键设计或 Sol 各层仍未解决的问题。

预览或安装 阅读中文 README

普通技术设计交给 Sol，Astra 留给关键设计和经 Sol 仍未解决的工作。预计这会减少普通任务进入 Astra 的次数。仓库尚未测量配额节省情况。

不确定当前任务适合哪个 pstack 技能？可以询问 /poteto-help。它会阅读已打包的指南，推荐相关技能，也可以提供一条示例提示词。单纯询问帮助不会开始执行推荐的工作。Codex 的模型选择和权限遵循本仓库的 GPT 配置。

明确交接边界

由一位主控负责决策

主控检查证据、选择方案并验收结果。子 Agent 接收范围明确的任务，带回改动、观察结果或阻塞原因。

角色职责
Sol 主控负责目标、约束、日常决策、协同和最终验收。
Luna 执行者处理常规实现和操作、按指定只读清单采集证据、运行指定检查，以及忠实落实已批准内容的修改，并将结果和证据交回主控。
Sol 高级执行者普通技术任务和 Luna 失败后的接管，从 gpt-6.1-sol、medium 开始。同一个未解决问题依次进入 Sol high 和 xhigh，之后才交给 Astra。新建的子 Agent 自主选择方案、实施和验证，不会切换正在运行的主控。
Astra 专家直接负责主架构或系统架构、关键接口和数据契约设计，以及会造成重大影响的设计取舍。其他任务仅在 Sol xhigh 报告无法解决、在本层 30 分钟评估时仍未解决，或用户明确选择 Astra 时交给 Astra。接管后自主诊断、选择方案、实施和验证，直到完成。先用 gpt-6-astra、high；仍未解决时交给新的 xhigh 专家子 Agent，自动升级到此为止。

常规执行交给 Luna。普通方案、计划、本地设计、现有规则的常规修改、上游适配和范围明确的咨询，直接交给新的 Sol 高级执行者，从 medium 开始。Luna 失败后的接管也从 Sol medium 开始。同一个未解决问题依次经过 Sol high 和 xhigh，之后才进入 Astra high；普通 Sol medium 或 high 任务不会跳过层级直接交给 Astra。主架构或系统架构、关键接口和数据契约设计、重大设计取舍可以直接交给 Astra。核心架构决策不交给 Luna。仅有“技术文档”这一标签或主控感到不确定，都不足以触发 Astra。关键设计问题、Sol xhigh 报告无法解决或在 30 分钟评估时仍未解决的问题，或用户针对当前任务明确选择 Astra 模型时，可以进行 Astra 只读咨询。普通咨询从 Sol medium 开始。所有咨询和子 Agent 均由主控派发。用户针对当前任务明确选择的模型和强度仍然优先。接管时使用通用执行角色，并明确指定模型和强度。现有角色 ID 和运行时权限不变。每个新任务从适用角色的默认强度开始，除非用户明确选择模型或强度；只有同一个未解决任务的升级交接才进入下一层。实际模型可用性取决于 Codex 宿主与账号。

并行执行彼此独立的工作

没有共用写入或依赖的文字与代码任务可以并行。生图、图片编辑、查看和传输一次只处理一项。

使用 Codex 已有的能力

PigeonStack 打包了指令、Codex 插件、配置和部署工具。它不提供 MCP 服务或单独的自主调度器。

执行者报告无法解决时，立即进入下一层。未提前报告失败时，主控在该模型和强度层级首次派发满 30 分钟后评估。同层级重试或替换执行者不会重置计时。升级时保留证据、失败尝试和累计耗时。现有等待可以中断；30 分钟是评估时点，不是强制等待时间。

常规工作从 Luna 开始时，升级路径为 Luna max、Sol medium、Sol high、Sol xhigh、Astra high，最后是新的 Astra xhigh 子 Agent。直接交给 Sol 的普通任务从 medium 开始；关键设计从 Astra high 开始。任务成功就结束升级。每个新任务从适用角色的默认强度开始，除非用户明确指定模型或强度；只有同一个未解决任务的升级交接才进入下一层。同层级重试或替换仍使用该层级且不会重置计时。高级执行者和专家自主选择、实施和验证完整方案，再将结果和证据交回主控最终验收。用户明确选择 Astra 的任务也遵循 high 到 xhigh 的自动升级上限。常规网页实现和重构仍由 Luna 处理，与任务规模无关。外部阻塞，包括所需模型或强度、凭据、访问、权限或服务不可用，不会触发推理升级。Astra xhigh 报告无法解决或在本层级 30 分钟评估时仍未解决，就停止升级并报告实际限制或证据缺口。不自动升到 Astra max、ultra，也不重启升级循环。已确认健康的长时间命令不是推理失败，继续现有观察流程。模型 ID 和角色详情见 MODELS.md。

需要 ComputerUse 的操作只由主控执行，因为子 Agent 没有这些工具。不要把需要 ComputerUse 的操作委派给子 Agent。高级执行者或专家可以请主控执行一项明确的 UI 操作并报告观察结果，然后继续处理同一个问题。这是请求观察结果，不是让主控决定解决方案。文字、代码、CLI 和 API 工作仍可委派。这条规则不增加工具或权限流程。

优先通过现有入口推进已授权的正常业务流程。实际遇到或收到 BUG 报告时，保留足够的证据，在授权范围内定位并修复原因，再重跑受影响的真实业务流程并完成针对性回归。遇到问题就处理，不必等整个流程结束。仅阻塞受影响的操作及其依赖操作，继续推进独立且有效的工作。真实流程不可用时，明确说明尚未验证的结果。针对性回归不代表获准运行全量测试。

校验门是操作继续前必须通过的强制检查。只有问题已被证据确认，或存在明确的当前要求时，才可新增校验门。不得将未经证实的猜测或假设的未来失败转化为新的校验门或前置条件。确认 BUG 也不意味着必须加门。确有需要时，将校验门限定在受影响的操作和边界内，验证它能捕获该问题或落实当前要求，且不无故阻断有效工作。现有必需检查、明确的当前要求，以及安全、权限和数据完整性边界，均在 BUG 发生前就适用。

适用人群

适合需要清晰交接的 Codex 用户

如果你需要明确的决策负责人、范围清楚的执行任务和基于证据的验收，可以了解 PigeonStack。

兼顾成本与能力是工作策略，不是跑分结论。模型 ID、账号权限、支持的推理强度和费用取决于你的账号与 Codex 客户端。

当前宿主要求

  • 维护中的配置已在 Windows 与 PowerShell 环境验证。
  • 同步脚本要求 Python 3.11 或更高版本。
  • 安装插件需要兼容的 Codex CLI，以及已注册并能解析 pstack@personal 的本地插件市场。
  • 多 Agent 工作需要宿主提供原生子 Agent 工具，并且账号可使用所选模型。

常见问题与边界

使用前需要了解什么

PigeonStack 是什么？

PigeonStack 是 PigeonYang 维护的一套 Codex 全局规则、Agent 角色定义、选定配置、定制版 pstack 插件和本地同步脚本。

PigeonStack 与 pstack 有什么关系？

PigeonStack 将 Lauren Tan 的 pstack 工作流适配到 Codex，并加入本仓库的规则和部署配置。它不宣称优于上游项目。页面链接到固定版本的上游源码，并保留原作者署名。

它是插件、MCP 服务还是 Skill？

PigeonStack 是一个代码仓库和部署配置，内含适配后的 Codex 插件与选定技能。它不提供 MCP 服务、定时任务、钩子或后台调度器。

可以选择其他模型吗？

仓库支持配置模型选项，本地规则也规定用户明确选择优先。你的 Codex 宿主和账号必须提供所选模型与 Agent 工具。仓库不验证服务商内部的模型映射。

预览和安装有什么区别？

独立预览使用 --codex-home 和 --skip-plugin-install 检查文件副本与配置合并。它不会激活插件，也不会改写指令中机器专属的路径。请看开始使用指南了解两种流程。

哪些结果经过验证？

同步检查成功表示受管理文件与配置在磁盘上保持一致。要确认指令已加载和实际模型路由，还需在新的 Codex 会话中验证。发布本网站不能证明搜索引擎已收录或页面获得排名。
